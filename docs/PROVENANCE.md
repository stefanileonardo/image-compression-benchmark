# Provenance of the results

Everything under `results/` was carried over from the original study folder, with two kinds of
change: **renaming to match verified content**, and **dropping regenerable
intermediates**. Nothing was recomputed during the migration — the fitted parameters and
reconstructions are the originals, byte for byte.

---

## SMoE configuration renaming

The original folders were named after the kernel budget they were *believed* to hold.
Reading the stored parameters showed that two of them did not. The number of kernels in a
tile is the length of the `pis` vector in `params_best.pkl`; an exact square means no
$\ell_1$ pruning occurred, so the budget is unambiguous.

| Original folder | Kernels/tile | Implied $K$ | Claimed $K$ | New location |
|---|---|---|---|---|
| `32k_100i_7899s` | 256 | **16** | 32 ❌ | `smoe_params/K016/` |
| `64k_100i_25201s` | 1024 | **32** | 64 ❌ | `smoe_params/K032/` |
| `96k_100i_43212s` | 8642–9017 | **≈96** (pruned from 9216) | 96 ✅ | `smoe_params/K096/` |
| `16k_100i_3535s` | 256 | **16** | 16 ✅ | `archive/smoe_duplicate_K016_run/` |

So the study covers **three** kernel budgets — 16, 32, 96 — not the four the original
folder names implied. There is no $K=64$ run.

`scripts/04_smoe_metrics.py` re-checks this at runtime via
`src.smoe.rate.implied_budget()` and prints a `MISLABELLED` warning if a folder ever
disagrees with its contents again.

### The disputed duplicate

`16k_100i_3535s` and `32k_100i_7899s` both hold $K=16$ parameters, and their **stitched
reconstructions are byte-identical across all five images**:

| Image | MD5 (first 16 hex) |
|---|---|
| Gradient | `737cb4b1ff050bb6` |
| Grass | `73c0077329b47c81` |
| Mixed | `b508febe041b8014` |
| Nature | `88e4ba549a29378d` |
| Sharp Edges | `6d3c4d7f58e220bc` |

Two independent stochastic training runs cannot produce identical files. One folder's
`results/` was copied from the other. Corroborating: `16k_100i_3535s` had per-tile
parameters for only three of the five images, so its top-level reconstructions could not
have come from its own tile data.

The complete run (5 images) is kept as `K016`. The partial one is preserved under
`archive/smoe_duplicate_K016_run/` so the evidence survives for whoever resolves this — it is
**not** loaded by any script and does not enter any table.

## What was dropped

The original SMoE tree was 2.1 GB. Only 22 MB of it is the scientific payload.

| Kept | Dropped |
|---|---|
| `params_best.pkl` per tile (215 files, 22 MB) — the fitted models, and the basis for every rate figure | TensorFlow checkpoints (433 sets: `.index`, `.meta`, `.data-00000-of-00001`) |
| Final stitched reconstructions (14 PNG) | Per-iteration parameter snapshots (`params/00000000_params.pkl`, …) |
| Wall-clock timing tables | Per-iteration reconstruction PNGs and per-tile `loss.png` |
| | `params_last.pkl` (superseded by `params_best.pkl`) |
| | Per-image tile crops (regenerable from `data/processed/` by `src.smoe.tiling`) |
| | Four near-duplicate copies of the upstream `tf-smoe` repository |

Everything dropped is either regenerable from what remains or is training scratch. The
originals are untouched in the parent project folder.

## Directory contents

```

├── metrics/
│   ├── classical.csv                ← every JPEG / JPEG 2000 / AVIF operating point
│   ├── smoe.csv                     ← SMoE rate (from parameters) + distortion
│   ├── all_operating_points.csv     ← the two above, concatenated

├── reconstructions/

```

## Regenerating

`metrics/`, `figures/` and `reconstructions/{jpeg,jpeg2000,avif}/` are all reproducible
from `data/processed/` plus `smoe_params/`:

```bash
python scripts/02_run_classical.py
python scripts/04_smoe_metrics.py
python scripts/05_aggregate.py
python scripts/06_make_figures.py
```

`smoe_params/` and `reconstructions/smoe/` require retraining
(`scripts/03_run_smoe.py`) — hours per image on a GPU. That is why they ship with the
repository.

**Expect the classical numbers to shift slightly if you regenerate them.** Codec output
depends on the libjpeg-turbo, OpenJPEG and libaom builds behind Pillow and `pillow-heif`;
that is why `requirements.txt` pins versions. The CSVs committed here record the
environment they came from in their header comment.
